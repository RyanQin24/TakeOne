This launches the real COM5 cart, COM9 phone arm and COM8 light arm using `data/robot-commissioning-ready.json`. Each arm has five motors; phone roll is ID 6 and light roll is ID 5. The Windows profile is enabled by the user's request to run the complete robot. Missing production measurements are recorded as qualification warnings; no missing values or verification flags have been filled with invented results.

`live` defaults to commissioning. Add `--qualified` to require the separate measured production qualification records. `--plan-start` requests the older behavior in which the operator must already have placed the arms at the first planned pose. The ordinary launcher captures the actual pose instead.

The launcher first takes three real encoder snapshots from each arm with torque already off. Under the operator's maximum-learning policy, a reading above a saved maximum increases that maximum to the largest captured value (within the ordinary 0..4095 encoder range). It writes the corresponding firmware endpoint, verifies readback and saves the active override. It preserves the original files and compensates the degree-normalization midpoint so the same raw reading keeps the same model angle. It makes no torque or goal-position writes. Lower limits are unchanged. This is a startup calibration operation; limits stay fixed during movement.

If maxima, geometry, configuration or planning sources changed, the launcher rebuilds and checks the same shot once, visibly reporting `repreparing_plan`. Changes limited to the explicit runtime file allowlist can reuse the locally checked trajectory after checking its saved bytes, refreshing provenance and repeating preflight; this reports `runtime_plan_refreshed`. Only the identity and provenance fields change in that case. It retains the previous plan, calibration and firmware reports under `data/commissioning/*-maxima-*`. Unchanged launches reuse the checked plan. Direct `motion.cli live` remains the lower-level executor; use the launcher for automatic maximum learning.

The subsequent live sequence is:

1. Print startup immediately. Validate plan content, current source hashes and the saved preparation receipt. IK runs in preparation/check, never in live startup or a device loop.
2. Apply the numerical joint limits and check the exact wheel packet schedule. Cart commands are zero or 0.04–0.05 in the configured direction, independently per wheel, for a finite timeline.
3. Read the real encoders on both arms with register writes prohibited. Report exact out-of-range joint names, IDs, values and calibration endpoints. Check mode and calibration correspondence.
4. When necessary, prepend a rest-to-rest quintic approach, keeping the cart stationary. Its duration uses the analytic derivative maxima and a 0.5 rad/s approach target. Check the complete curve against calibration, the same nominal geometry clearance screen and command policy. A rejected approach is saved for inspection, never executed.
5. Reopen one serial owner per device and recheck the actual arm start before torque activation. Activate using acknowledged Goal → Torque Enable → the same Goal. Readback is monitored throughout motion.
6. Use one monotonic epoch for the cart and both arms. Print progress every second and publish worker faults immediately. Send the cart's exact timed left/right schedule; no absolute origin or measured distance is required to send it.
7. Finish with cart zero commands and retained arm goals. Type `abort` to stop travel. Support both arms before typing `release` to turn torque off.

The reference shot still has nine seconds of cart commands inside a 13-second arm plan. Any initial approach adds time before that plan, without changing the original shot or wheel commands. The local cart start is `(0, 0, 0)`. The model predicts the resulting displacement; the controller does not claim that a successful UART write measured physical travel.

The command policy is explicit in `configs/arm-execution.json`: continuous speed 0.8 rad/s, acceleration 1.8 rad/s² and jerk 20 rad/s³, shared with the planner. The jerk cap was revised from 12 for the bounded transition, whose calculated peak was 15.84; this is a policy revision, not a measurement of motor performance. It checks a 0.04 rad maximum commanded step, 0.035 rad start tolerance, 0.15 rad tracking tolerance and 0.05 rad settling tolerance. These are commissioning settings, not measurements of servo capacity. Integer-command derivative checks account for the exact one-count quantization bound, rather than interpreting encoder quantization as physical acceleration or jerk. The onboard servo PID, speed and acceleration settings are preserved.

Run records distinguish `command_policy` from `measured_limits`. `robot_movement_verified` stays false until independent observations support that conclusion. Calibration originals, the operator's endpoint revisions, real device health checks, timeouts and failure handling remain in use.
